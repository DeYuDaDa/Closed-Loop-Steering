## 🔬 可行性论证：推理时干预与 Per-Slot 架构的相容性

### 前提：当前干预系统的完整数据流

当前 `Dynamic_Spherical` 模式在每个 token 生成步骤中，存在一条**完整的闭环反馈链**：

```
[GPU: model.generate] ──→ LogitsProcessor 被调用
   ├─ InfNanProtectionProcessor   (logits 清洗)
   ├─ ActiveMaskProcessor         (检测已完成的序列)
   └─ StateMonitor.__call__()     (核心闭环)
         ├─ 计算 H_t (Shannon 熵)
         ├─ 更新 EMA 熵
         ├─ 检测 ThinkBrake Margin
         ├─ 调用 PIDController.step() → 输出 α
         └─ α 写入 state.alpha
         ↓
[GPU: 同一个 token 的前向传播中]
Forward Hook (register_forward_hook on layer[LAYER_ID])
         └─ 读取 state.alpha
         └─ 执行 SLERP 旋转 → 修改 hidden state
```

> **关键约束**：`LogitsProcessor` 的输出（`state.alpha`）必须在**同一个 token 的下一步前向传播**中被 hook 读取。这在 `model.generate()` 中能成立，因为 generate 循环是 `前向 → 采样 → 更新 input_ids → 再次前向`，而 hook 在下一步前向时读取上一步 processor 写的 alpha。

---

### 逐模块相容性分析

#### ✅ 模块一：State Monitor（EMA 熵 + ThinkBrake）

**是否可迁移到 per-slot？ → 完全可行**

- `InjectionState` 当前已经是 `batch_size` 维的张量设计（`ema_entropy: [B]`，`alpha: [B]` 等）
- Per-slot 模式中，每个 slot 拥有**独立的 `InjectionState(batch_size=1)`**，所有张量退化为 scalar
- `StateMonitor.__call__(input_ids, scores)` 接收的 `scores` shape 从 `[B, V]` 变为 `[1, V]`，代码无需修改
- EMA 状态（`ema_entropy`，`step_count`）完全 per-slot 隔离，**无跨序列污染风险**
- ThinkBrake Latch（`is_converged`）为 bool tensor，slot 完成后随 slot 销毁，干净

**结论**：`InjectionState` 的 batch 维度已是抽象层，只需将 `batch_size=1` 传入即可。

---

#### ✅ 模块三：PID/TAE Controller

**是否可迁移到 per-slot？ → 完全可行**

- `PIDController` 的内部状态是 `[batch_size]` 的张量（`prev_error`，`integral`）
- Per-slot 时 `batch_size=1`，退化为 scalar tensor
- PID 的 `step()` 方法只依赖当前 `entropy` 和内部历史误差，**与其他 slot 无任何交互**
- 每个 slot 在创建时 `new PIDController(batch_size=1)`，销毁时自然释放

**结论**：无需任何代码修改，直接用 `batch_size=1` 实例化即可。

---

#### ⚠️ 模块四：SLERP Forward Hook — **这是唯一的关键挑战**

**核心问题**：`register_forward_hook` 是注册在**模型层对象**上的，作用于整个 forward pass，不区分 slot。

**在 multi-slot 推理中，存在以下三种 hook 设计选项：**

##### 方案 A：每个 slot 串行执行 forward，hook 在 slot 粒度动态挂载/卸载

```python
# 每个 slot 独立执行一步推理
for slot in active_slots:
    # 给本 slot 挂载专属 hook（捕获 slot.state）
    handle = layer.register_forward_hook(slot.hook_fn)
    
    with torch.no_grad():
        out = model(input_ids=slot.last_token,
                    past_key_values=slot.past_key_values,
                    attention_mask=slot.attention_mask,
                    use_cache=True)
    
    handle.remove()  # 立即卸载，不影响下一个 slot
    slot.past_key_values = out.past_key_values
    # hook_fn 内部已通过 slot.state.alpha 完成了 SLERP 操作
```

- **优点**：逻辑最清晰，每个 slot 的 hook 完全隔离，`state.alpha` 无歧义
- **缺点**：串行循环，每次 forward 是 `batch=1`，GPU tensor core 利用率低
- **适用场景**：slot 数 ≤ 8，或问题对正确性要求高

##### 方案 B：所有 slot 合并成 padded mini-batch，用单一 hook 区分 slot

```python
# 将所有 slot 的 last_token 合并
batch_input = torch.cat([s.last_token for s in active_slots], dim=0)  # [N, 1]

# 单一 hook，通过 batch 维度区分不同 slot 的 alpha
def merged_hook(module, args, output):
    hidden = output[0]  # [N, 1, d]
    for i, slot in enumerate(active_slots):
        alpha_i = slot.state.alpha  # slot 专属 alpha
        h_i = hidden[i:i+1, :, :]  # 取第 i 个序列
        hidden[i:i+1, :, :] = spherical_rotate(h_i, control_vector, alpha_i)
    return (hidden,) + output[1:]

handle = layer.register_forward_hook(merged_hook)
out = model(input_ids=batch_input, ...)  # 合并前向
handle.remove()
```

- **优点**：GPU 利用率接近原始批处理，tensor core 效率最高
- **缺点**：KV cache 的批量管理极其复杂（每个 slot 的 KV cache 长度不同，无法直接 concat），需要实现动态 padding + mask
- **可行性评估**：在 per-slot 长度差异大的情况下，KV cache 不能合并 → **技术上可行但工程复杂度极高**

##### 方案 C：分离 StateMonitor 调用与 hook（推荐实用方案）

**洞察**：`LogitsProcessor` 和 `hook` 之间的唯一通信是 `state.alpha`。  
在 continuous batching 的手动 token 循环中，我们**不需要** `LogitsProcessor` 框架——可以直接手动调用 `StateMonitor`：

```python
# 手动控制流（每个 token step）
for slot in active_slots:
    # Step 1: 先获取 logits（用 past_key_values 做单步前向，不带 hook）
    out = model(input_ids=slot.last_token,
                past_key_values=slot.past_key_values, use_cache=True)
    logits = out.logits[:, -1, :]  # [1, V]
    
    # Step 2: 手动调用 StateMonitor 更新 state.alpha
    slot.monitor(slot.current_ids, logits)  # 更新 slot.state.alpha
    
    # Step 3: 用更新后的 alpha，手动对 hidden state 执行 SLERP
    # ⚠️ 问题：此时 forward 已经结束，hidden state 已经参与了 lm_head 的 logits 计算
    # hook 的 SLERP 作用于 hidden state → lm_head → next token 的 logits
    # 这里 logits 已经是 "干预前" 的，需要把 SLERP 放在 "next step" 的前向里
```

> [!WARNING]
> **方案 C 存在一个时序问题**：在原始 `model.generate()` 流程中，hook 在 forward 内部作用于 hidden state，然后 lm_head 用被修改的 hidden state 生成 logits，StateMonitor 再处理这些 logits。  
> 这意味着：**t 步的 SLERP** 作用于 **t 步的 hidden state**，影响的是 **t 步的 logits**（进而影响 t 步采样的 token），而 **t 步的 alpha 由 t-1 步的 StateMonitor 写入**。  
> 准确的时序是：`alpha[t-1] → hook(t) → logits(t) → StateMonitor(t) → alpha[t] → hook(t+1)`

**方案 C 的正确实现**：在 prefill 阶段注册 hook，decode 阶段始终保持 hook 挂载，手动在 forward 前设置好 `state.alpha`（即上一步 StateMonitor 的输出），让 hook 在本次 forward 中读取：

```python
# decode loop for one slot (simplified)
for step in range(max_new_tokens):
    # Hook 已挂载，读取 slot.state.alpha（上一步 monitor 写的）
    out = model(input_ids=slot.last_token,
                past_key_values=slot.past_key_values, use_cache=True)
    # hook 内部已用 state.alpha 做了 SLERP
    
    logits = out.logits[:, -1, :]  # [1, V]
    
    # 手动调用 monitor，为下一步更新 alpha
    slot.monitor(slot.current_input_ids, logits)
    
    # 采样下一个 token
    next_token = sample(logits)
    slot.last_token = next_token
    slot.past_key_values = out.past_key_values
    
    if is_eos(next_token):
        break
```

**优点**：  
- 时序与 `model.generate()` 完全一致，实验结果可复现  
- Hook 的挂载/卸载在 slot 创建/销毁时（不是每步），开销小  
- 每个 slot 串行执行 forward，`state.alpha` 无跨 slot 竞争

**缺点**：每步 batch=1 forward，GPU 利用率取决于 `max_concurrent_seqs` 的大小

#### ✅ 模块二：PCA 流形投影（离线预处理）

**是否影响 continuous batching？ → 完全不受影响**

- PCA 流形投影是**离线完成**的（在 `extract_critic_vector.py` 中），产出 `v_purified.pt`
- 在推理时，`control_vector` 已经是固定的纯化向量，作为只读参数传入 hook
- 无论 batch=1 还是 batch=16，control_vector 是相同的全局常量

#### ✅ 模块五：DTR 评估（离线事后计算）

**是否影响 continuous batching？ → 完全不受影响**

- DTR 计算在 `evaluate_dtr_offline.py` 中完全离线执行，输入是已保存的 `output_ids`
- 只需确保每个 slot 完成后，正确保存 `output_ids`、`input_len`、`alpha_trajectory` 等字段
- `intervention_start` / `intervention_end` 的 step 计数需从 slot 的 `state.step_count` 中读取

### 总结：可行性裁定

| 模块 | 组件 | per-slot 兼容性 | 需要修改？ |
|------|------|----------------|----------|
| 模块一 | `InjectionState` | ✅ 已是 batch 抽象，`batch_size=1` 直接用 | 无 |
| 模块一 | `StateMonitor` | ✅ 每 slot 独立调用，scores=[1,V] | 无 |
| 模块三 | `PIDController` | ✅ `batch_size=1` 直接用 | 无 |
| 模块三 | `TAEController` | ✅ 同 PID | 无 |
| 模块四 | Forward Hook | ⚠️ **需要选择挂载策略** | 需设计 |
| 模块四 | `create_steering_hook` | ✅ hook 本身逻辑不变，只需每 slot 独立注册 | 无 |
| 模块二 | PCA 向量 | ✅ 全局只读常量 | 无 |
| 模块五 | DTR 计算 | ✅ 离线，只需收集输出 | 无 |

**唯一需要工程设计的点**：**Forward Hook 的 per-slot 挂载/卸载策略**（推荐方案 A：串行 + 每 slot 独立 handle，时序正确性最高）。

**最终结论**：✅ **方案完全可行**。所有干预组件（EMA、PID、SLERP）均以 `batch_size` 为抽象维度，天然支持 `batch_size=1` 的 per-slot 使用。唯一的实现难点是 hook 的串行管理策略，但这是标准 PyTorch 用法，无需修改任何现有模块代码。

## Problem

当前 `run_batched_generation` 使用 HuggingFace 的 `model.generate()` 做静态批处理：一批 `batch_size=16` 的样本必须等到**最后一个样本生成 EOS** 才能结束。  
如果 14 个样本在 1-2k token 结束，但 2 个样本跑到 8-16k，整批的计算量都扩展到 8-16k，浪费 4-5x 算力。

**解决方案：Continuous Batching（连续/动态批处理）**  
一旦某个槽位（slot）生成完成，立即用下一个等待的 prompt 填充该槽位，保持 GPU 永远处于满负荷的有效计算状态。

> [!IMPORTANT]
> 由于 HuggingFace `generate()` 不支持原生的 continuous batching，必须手动实现 **token-by-token 的自回归推理循环**，利用 `past_key_values` (KV cache) 避免重复计算 prefill。

---

## 核心架构设计

### Slot 设计

每个 `Slot` 代表推理池中一个独立的推理位置（类似单张"椅子"）：

```python
@dataclass
class Slot:
    idx: int                   # 在 pending_prompts 中的原始序号
    input_ids: Tensor          # [1, seq_len] — 当前序列的全部 token
    attention_mask: Tensor     # [1, seq_len]
    past_key_values: ...       # KV cache（初始为 None，prefill 后填充）
    input_len: int             # 原始 prompt 长度
    n_generated: int           # 已生成的 token 数
    done: bool                 # 是否已完成
    # per-slot controller state
    state: InjectionState      # 独立的状态对象
    pid: PIDController | None  # 独立的 PID/TAE 控制器
```

### 推理循环设计

```
初始化阶段:
  ┌─────────────────────────────────────────────────────┐
  │  pending_prompts = 所有 prompt (queue)              │
  │  active_slots = []                                  │
  │  填充至 max_concurrent_seqs 个 slot (做 prefill)    │
  └─────────────────────────────────────────────────────┘

生成循环 (直到所有 prompt 完成):
  ┌─────────────────────────────────────────────────────┐
  │  1. 对所有 active_slots 的 last token 做一步前向     │
  │     注意：每个 slot 独立调用 model(...) 以便精确     │
  │            控制 KV cache 和 hook 作用范围           │
  │     ⚠️ 这里有两种策略，见下文                       │
  │  2. StateMonitor / steering hook 逐 slot 调用       │
  │  3. 采样下一个 token                                │
  │  4. 检测 EOS 或 max_new_tokens → 标记 slot.done    │
  │  5. 完成的 slot → 收集结果 → 用新 prompt 替换       │
  └─────────────────────────────────────────────────────┘
```

### 前向策略选择

**策略 A（推荐）：每步对每个 slot 独立做单步前向**  
- 优：每个 slot 有独立的 KV cache，无 padding 浪费，实现最简单
- 缺：batch=1 前向，GPU 利用率略低于合并批处理
- 适合：`max_concurrent_seqs` 较大时（≥8）效果好，完全消除 padding 浪费

**策略 B：将所有 active slots 合并成一个 padded batch 做一步前向**  
- 优：GPU 矩阵乘法效率最高
- 缺：需要 KV cache 的批量管理，不同长度槽位合并极复杂
- 不推荐，复杂度极高

**选择策略 A**，实现简洁，自然消除 straggler，且多个 slot 真正并行可通过加大 `max_concurrent_seqs` 来补偿。

新增 `run_continuous_batching_generation` 函数，**替代** `run_batched_generation` 中的 `model.generate()` 调用。  
原有 `run_batched_generation` 保留（`USE_CONTINUOUS_BATCHING=False` 时使用）。

**新函数签名：**
```python
def run_continuous_batching_generation(
    model, tokenizer, prompts: list[str], mode: str,
    control_vectors: dict,
    max_concurrent_seqs: int = MAX_CONCURRENT_SEQS,
) -> Generator[list[dict], None, None]:
```

**关键实现细节：**

1. **Prefill 阶段**：对新进入 slot 的 prompt 做一次前向以建立 KV cache
   ```python
   with torch.no_grad():
       out = model(input_ids=slot.input_ids, attention_mask=slot.attention_mask,
                   use_cache=True, return_dict=True)
   slot.past_key_values = out.past_key_values
   next_logits = out.logits[:, -1, :]  # 用于第一步采样
   ```

2. **Decode 步骤**：每步输入当前 token（shape `[1,1]`），传入 KV cache
   ```python
   out = model(input_ids=next_token, attention_mask=slot.attention_mask,
               past_key_values=slot.past_key_values, use_cache=True)
   slot.past_key_values = out.past_key_values
   ```

3. **Steering hook 管理**：每个 slot 有独立的 `InjectionState`，hook 通过闭包捕获当前 slot 的 state，**在 prefill 后注册，slot 结束后移除**

4. **StateMonitor 调用**：不再依赖 HF 的 `logits_processor`，改为在采样前手动调用：
   ```python
   # 模拟 LogitsProcessor 链
   logits = infnan_processor(current_ids, logits)
   logits = monitor(current_ids, logits)  # 更新 state.alpha
   next_token = sample(logits)
   ```

5. **Slot 回收与填充**：
   ```python
   for slot in done_slots:
       results.append(slot_to_result(slot))
       if pending:
           new_slot = init_slot(pending.popleft())
           active_slots[slot.pos] = new_slot
       else:
           active_slots.remove(slot)
   ```

6. **结果 yield**：每当有 `batch_size` 个 prompt 完成，yield 一批结果（保持与旧接口兼容）

**`run_full_experiment` 中的调用切换：**
```python
if USE_CONTINUOUS_BATCHING:
    gen_iterator = run_continuous_batching_generation(...)
else:
    gen_iterator = run_batched_generation(...)
```
